Sarus Firmware Plan

How Sarus builds its own ArduPilot firmware for Plane (QuadPlane included), Copter and Rover, what the second release adds, how a release reaches the Install Firmware page, and what comes next.

01Where it stands

Sarus firmware now comes in two lines. The 4.7 line lives on the branch sarus-4.7.1 of github.com/LikhitS/ardupilot and starts from ArduPilot's stable 4.7.1, where Plane, Copter and Rover share one commit. The 4.6 line lives on sarus-4.6.3 and starts from Copter 4.6.3. That commit is Plane 4.6.3 and Rover 4.6.3 plus a one-line fix to Copter's version file, so all three vehicles are built from exactly their official 4.6.3 source.

The first release, Sarus-1, changed only the name. The second, Sarus-2, is the same on both lines and adds two things. The parameter lock refuses setup changes from any ground station until it proves it holds the owner's admin password; flying stays open to everyone. The firmware also gains room for the owner's parameter set as its defaults. The aircraft identify themselves as, for example, ArduPlane V4.7.1 Sarus-2 or ArduCopter V4.6.3 Sarus-2; the Ardu… V prefix stays because ground stations use it to tell a QuadPlane from a Copter.

GitHub's cloud machines build both lines for seven board families: CubeOrange, CubeOrangePlus, Pixhawk6X, Pixhawk6C, Pixhawk1, fmuv3 and MatekH743. All 42 board builds of Sarus-2 compile and pass their checks.

02The parameter lock

While locked, the aircraft refuses parameter writes and sends back the value it keeps, and it refuses parameter resets, every calibration, reboot into the bootloader, bootloader flashing, SD card formatting, receiver pairing, Lua scripting commands, OSD parameter changes, MAVLink signing setup and any file write over MAVLink FTP. FTP writes are included because a parameter file written there loads parameters, and a script copied there can set them. A plain reboot, missions, modes, arming and flying stay open.

The aircraft holds only Ed25519 public keys: the owner's key and a spare, both created on the owner's PC on 6 October 2026. The private key behind each one is derived from its password with scrypt and exists only inside Sarus Operation Planner while someone who typed the password has it unlocked. To unlock, Sarus asks the aircraft for a one-time number and returns it signed. A number is good for one attempt, for 30 seconds, from the station and link that asked for it, so a recorded unlock cannot be replayed. The unlock belongs to that station on that link. It ends on reboot, on a lock request, or after 10 seconds of silence once disarmed; it is never cut off in flight, but a new one is refused while armed.

What the lock does not cover

Someone with the board on a bench can still flash other firmware through the USB bootloader. Closing that gap needs ArduPilot's secure bootloader with a Sarus signing key, the next step below. Settings inside DroneCAN peripherals are not covered either.

04The firmware's own limits

The request was to stop the firmware overriding values the owner sets. We wrote every parameter of QuadPlane, Copter and Rover, about 3,000, to the simulator and compared what each aircraft kept. Only one is a genuine limit. Loiter acceleration (LOIT_ACC_MAX_M, Q_LOIT_ACC_MAX_M) is capped at g·tan(maximum lean angle), because a multirotor tilted to 30 degrees can only accelerate sideways at about 5.66 m/s² without losing height. Raising the cap would not make the aircraft faster; it would only make the controller ask for something it cannot do. The other differences are values the firmware measures itself (barometer ground pressure, device IDs, mission count) and parameters stored in 8 bits, which stop at 127. Changing their storage would scramble the parameters of every aircraft already flying.

So Sarus-2 removes no limit. The ground station instead shows the value the aircraft actually holds after every write, and the new airframe limits page flags values beyond what the airframe can do, without changing them.

05The owner's parameter set as defaults

Most boards have no room for embedded defaults, so every Sarus board build now reserves 8 KB for them. When the owner's file is placed in Tools/sarus/defaults as plane.parm, copter.parm or rover.parm, each build merges it into the firmware: a new board, a parameter reset or a firmware install then starts from the owner's values, and where a board ships defaults of its own, the owner's value wins. Values that belong to one aircraft (sensor calibrations, device IDs, radio calibration, barometer ground pressure) are dropped automatically, and a file too large for the firmware stops the build with a message. Every board build also proves the merge on a scratch copy. The owner's files have not been supplied yet; until they are, the firmware starts from ArduPilot's defaults.

Firmware listmanifest.json on sarus-manifest, one release per line
Sarus Plannerreads it at start-up next to ArduPilot's list

The firmware list is made by ArduPilot's own manifest script, unchanged, so board IDs, USB IDs and bootloader names are exactly the ones ArduPilot publishes. The list keeps one current release per type and version line, so publishing for 4.6 never removes 4.7. When a board matches several builds, Install Firmware opens the selection window Mission Planner already has. The release step refuses to publish firmware that carries no owner key, so the lock can never ship switched off.

07Next steps

First, the owner tries the password on a simulator built with the owner keys, using tests\try-your-password.ps1; nobody else can, because nobody else knows it. Then both lines are tagged as Sarus-2 releases. After that the team flashes real boards and runs the Field Test Checklist, which now includes the lock, the airframe limits and the alarm.

Later steps, each with simulator evidence and a sign-off: the secure bootloader so that only Sarus-signed firmware runs; the owner's default parameter files; and more board families, up to everything ArduPilot supports, which would mean one release per vehicle type because of GitHub's size limits.

08Decisions taken

09Licensing

ArduPilot is licensed under the GPL version 3. Sarus firmware may be sold or supplied with aircraft, provided anyone who receives it can get the complete source of the build they received; the public fork does that. The lock's source is public too, and its security rests on the owner's password, not on the code being secret. Saying the firmware is based on ArduPilot is fine; suggesting ArduPilot endorses it is not.
