01Summary

Sarus Operation Planner is the Windows program our pilots use to set up, plan, fly and review ArduPilot aircraft. We built it from ArduPilot Mission Planner 1.3.83 and left every screen, button, feature and keyboard shortcut where Mission Planner has it.

Four things changed. The program now carries the Sarus name, logo, colours and installer, and it sits next to an existing Mission Planner installation without touching it. Parameter editing no longer stands in the way of tuning: a value outside ArduPilot's recommended range turns amber instead of being refused, and after each write the program asks the aircraft what it actually kept. We also found a fault, inherited from Mission Planner, that let replies from the aircraft go missing when two requests were waiting at once. That is fixed. Finally, every change is now compiled, tested, packaged and test-installed by GitHub's cloud machines, with no manual steps.

Alongside the program, Sarus now has its own firmware line: an ArduPilot 4.7.1 fork that identifies itself as Sarus and is built automatically for seven flight-controller families.

02The basics

Readers new to drone software may find this chapter useful. Abbreviations are explained in chapter 10.

Three parts of one system

An ArduPilot drone has three software-related parts. On the aircraft sits the flight controller, a small computer that reads gyroscopes, accelerometers, compass, GPS, barometer and airspeed hundreds of times a second and drives the motors and control surfaces. It runs the firmware, which decides how the aircraft flies: stabilisation, flight modes, missions, failsafes. Roughly 1,000 to 1,500 settings, called parameters, adjust that behaviour. On the ground, the ground control station shows what the aircraft is doing and lets the operator plan missions, change parameters, calibrate sensors, install firmware and download logs. Sarus Operation Planner is that ground station; ArduPilot, and now the Sarus fork of it, is the firmware; the flight controllers are off-the-shelf Pixhawk-class boards.

MAVLink

Aircraft and ground station talk in MAVLink, a compact message format. The aircraft streams its attitude, position and battery state several times a second. The ground station sends requests, such as "what is TECS_CLMB_MAX?" or "switch to AUTO", and waits for the matching answer. Radio links drop messages now and then, so the ground station has to notice a missing reply and ask again.

Mission Planner

Mission Planner is the free, open-source ground station written by Michael Oborne and the ArduPilot community. It is the most complete ArduPilot ground station for Windows and the one most ArduPilot pilots learn on. Its licence, the GNU GPL version 3, lets any company copy, change and sell it, on one condition: the changed source code must be published under the same licence.

QuadPlane

Our main airframe is a QuadPlane, a fixed-wing aircraft with four extra lift motors. It takes off and lands like a multirotor and cruises like an aeroplane, and ArduPilot Plane flies both phases. Speed and height in winged flight are handled by a controller called TECS. Being able to tune TECS and the VTOL (Q_) parameters without the ground station getting in the way was one of the main requirements for this project.

04How the work was done

A stable starting point

We took Mission Planner's last stable release, 1.3.83, rather than its development branch, which did not compile at the time. Before changing anything we built and tested the stock program to have something to compare against. It passed 3 of 3 simulator flights. Seven of its 38 unit tests failed, and they fail the same way in Mission Planner itself.

Small changes, one at a time

The work went in as 18 separate commits, each with a description, so any one of them can be reviewed or undone without touching the others. Where Mission Planner already offers a way to customise something (theme files, menu icon overrides, the logo file, the application name), we used it instead of editing program logic. Name replacements in the source were made by script, and the script stops if the number of replacements differs from what was expected.

A test pilot made of software

Most of the testing was done by a test harness we wrote for this project. It starts the real Sarus program, connects it to ArduPilot's simulator and then works the program the way a pilot would: connecting, opening every screen, changing parameters, uploading missions, arming, flying and pressing shortcuts, checking the result each time. Each test was run against stock Mission Planner first, so every Sarus result has a Mission Planner result next to it.

Builds in the cloud

The source code is public at github.com/LikhitS/SarusOperationPlanner, as the GPL requires. Each change pushed there is compiled on a GitHub Windows machine, unit-tested and packaged as an installer. Two more fresh Windows machines then install it silently next to a stock Mission Planner, start it, leave it running for a minute and uninstall it. Pushing a version tag such as v1.0.0 publishes the result as a GitHub release, which is where both the download page and the program's own updater look for new versions.

5.2 Parameter editing

In Mission Planner, typing a value outside the recommended range brings up a Yes/No question for every such value, read-only parameters cannot be changed at all, and the table shows whatever was typed even if the aircraft rounded or limited it. Sarus handles all three differently. Out-of-range values are accepted without a question; the cell turns amber and its tooltip gives the recommended range. A read-only parameter can be changed after a clear warning. And once a write is done, the program reads every written value back from the aircraft. Anything the aircraft did not keep is listed in a "Values changed by aircraft" window, and the table shows the real value.

Found during testing

Asked to set Q_LOIT_ACC_MAX_M to 9.81, the aircraft confirmed it and then ran at 5.66. Mission Planner would have shown 9.81. Sarus shows 5.66 and says so.

5.3 Lost replies

When Mission Planner waits for an answer from the aircraft, the waiting code reads incoming messages one by one and throws away whatever it is not waiting for. That works until two parts of the program wait at the same moment, say a background camera query while the pilot reads parameters. Then one of them can pick up the other's reply and discard it. The aircraft answered; the pilot still gets "timeout" or "command failed".

In Sarus, a request first registers for the reply it expects and only then sends the question. Every waiting request gets its own copy of each incoming message, so nothing can be taken from it. This now covers parameter reads and writes, command acknowledgements, commands with coordinates, mission upload and download, setting the current waypoint, and the flight-log list. 5.4 Other Mission Planner faults we fixed

The update check showed an error whenever the update server had no file yet; it now reports quietly that there is no update. Plugins compiled by an older version were reused after an upgrade and then failed every second, so the plugin cache now includes the program's build identity. The updater used to download a whole release file just to learn its size, where reading the size header is enough. When a legacy rally-point request was lost, the retry went out as a fence request and could never succeed; it now sends the right message.

The silent-install problem took longest to find. Mission Planner's installer starts a USB driver wizard that waits for a click. In a silent installation (msiexec /qn, as IT departments use) nobody can click, and the installation never ends. Stock Mission Planner hung there on both of our test machines. Sarus runs that driver step quietly when the installation is silent; normal installations are unchanged. In a silent install Windows adds only drivers whose publisher is already trusted, which keeps the same trust model as Mission Planner.

The parameter sweeps leave out the simulator's own physics settings (SIM_*) and the identity and link settings whose change would cut the test's connection.

What the tests showed about ArduPilot

The sweeps also exposed firmware behaviour that every ground station inherits, and which Sarus now reports to the pilot. Q_LOIT_ACC_MAX_M and LOIT_ACC_MAX_M are limited after the aircraft has accepted them. EK3_BCN_DELAY, EK3_FLOW_DELAY and LAND_THR_SLEW are stored in 8 bits and stop at 127, although their documentation allows more. The firmware overwrites BARO*_GND_PRESS by itself, and MIS_TOTAL cannot be written. In the simulator, parameter storage fills up after about 600 changed values. These are the first candidates for changes in the Sarus firmware.

07What it gives Sarus

Pilots lose nothing. The screens and shortcuts are the ones every ArduPilot pilot already knows, so existing Mission Planner tutorials still apply. What they gain is fewer false "timeout" and "command failed" messages, which matters most on long-range radio links, a parameter table that shows the values the aircraft is actually using, and room to tune the QuadPlane without being stopped by warnings.

For the company the gain is control. Sarus can ship a ground station under its own name with its aircraft, choose when to release, and fix problems without waiting for another project's schedule. The build and release pipeline is repeatable and tested, so a release does not depend on one person's laptop. It is also the base for the Sarus firmware and for the Linux, macOS and Android versions that come later.
